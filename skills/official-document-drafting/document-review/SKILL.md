# 公文审核

## 概述

对公文进行逐段审核，通过与权威党建平台实时对比，检查政治表述准确性、时效性和规范性，输出带分级批注的审阅版本。

## 审核范围

覆盖《党政机关公文处理工作条例》规定的全部法定文种：决议、决定、命令（令）、公报、公告、通告、意见、通知、通报、报告、请示、批复、议案、函、纪要。审核领域为党建 + 政治。

格式要素（标题三要素、主送机关、落款署名、成文日期、附件说明、章节序号）由系统确定性检查，本技能聚焦内容审核。

## 审核流程

```
用户上传文档
  → 文档解析（提取纯文本，保留段落结构）
  → 内容分析（LLM 识别主题、关键政治表述、引用文件）
  → 实时权威检索（Tavily 搜索共产党员网 + 党建网）
  → 分级对比审核（LLM 逐段对比）
  → 生成带 Word 原生批注的审阅文档
```

## 三级审核标准

### 🔴 严重（必须修改）
- 政治表述与权威文件明显矛盾
- 引用的文件/会议/讲话名称错误
- 领导人称谓、职务不完整或不准确
- 固定政治表述有原则性错误

### 🟡 重要（建议修改）
- 引用的文件非最新版本
- 提法已过时，有更准确的现行表述
- 专有名词表述与标准提法有偏差
- 该类型公文应有的固定表述缺失

### 🔵 建议（可选优化）
- 措辞可更规范（给出公文用语建议）
- 段落结构可优化
- 可补充的权威论据

## 文字与结构审核标准

对应需求 3.3(1)：错别字、语句表达、用词规范性、文章结构合理性。

### 🔴 严重（必须修改）
- 错别字、多字、漏字——尤其是固定提法、文件名称、领导职务、人名地名中的错字
- 语句不通、成分残缺或搭配不当，影响文意理解
- 数据、日期、人名、职务、单位名称与实际不符

### 🟡 重要（建议修改）
- 用词不规范：口语化表述、网络用语、非公文语体（如"搞定""立马"等）
- 表述歧义或语义冗余
- 结构不合理：层次不清、逻辑跳跃、段落功能混乱
- 标点符号使用不当（尤其书名号、引号、顿号的误用）

### 🔵 建议（可选优化）
- 语句可更精炼
- 措辞可更严谨、庄重

## 文种格式要点

按调用方传入或自动识别的文种，聚焦以下格式规范审核。标题分行排版（机关名称、事由、文种各占一行）视为完整标题，不得报"标题缺少要素"；成文日期月日不编虚位。

### 决议
- 标题：会议名称 + 决议主题 + 文种（如"XX会议关于……的决议"）
- 无主送机关；正文：审议情况 → 决议事项
- 落款：会议名称 + 通过日期

### 决定
- 标题：发文机关 + 事由 + 文种（如"关于……的决定"）
- 主送机关：发给下级机关时顶格书写，后加全角冒号
- 正文结构：背景缘由 → 决定事项 → 执行要求
- 结尾常用"本决定自发布之日起施行"等

### 命令（令）
- 标题：发令机关（或领导人职务）+ 事由 + 文种（如"关于……的命令"；公布令可用"主席令"式）
- 一般无主送机关；正文简洁：令由 → 命令事项 → 执行要求
- 落款：发布机关或领导人署名 + 成文日期；结尾"此令"

### 公报
- 标题：发布机关 + 事由 + 文种（如"……会议公报"）
- 无主送机关；正文：会议/事项概况 → 主要结论或决定
- 落款：发布机关 + 成文日期

### 公告
- 标题：发文机关 + 事由 + 文种（如"关于……的公告"）
- 无主送机关；正文：公告缘由 → 公告事项 → "特此公告"
- 落款：发文机关署名 + 成文日期

### 通告
- 标题：发文机关 + 事由 + 文种（如"关于……的通告"）
- 无主送机关；正文：通告缘由 → 规定性事项 → "特此通告"
- 落款：发文机关署名 + 成文日期

### 意见
- 标题：发文机关 + 事由 + 文种（如"关于……的意见"）
- 主送机关：顶格书写，后加全角冒号
- 正文结构：缘由 → 意见事项（分条）→ 执行要求
- 结尾常用"以上意见，请结合实际贯彻执行"

### 通知
- 标题：发文机关 + 事由 + 文种（如"关于……的通知"）。标题可分多行排版（机关名称、事由、文种各占一行），分行书写的三要素齐全即为完整标题，不得报"标题缺少要素"
- 主送机关：顶格书写，后加全角冒号
- 正文结构：通知缘由 → 通知事项 → 执行要求
- 落款：发文机关署名 + 成文日期，成文日期用阿拉伯数字

### 通报
- 标题：发文机关 + 事由 + 文种（如"关于……的通报"）
- 主送机关：顶格书写，后加全角冒号
- 正文结构：主要情况 → 分析评价 → 处理决定/要求（表彰、批评、情况通报）
- 结尾常用"特此通报"

### 报告
- 标题：发文机关 + 事由 + 文种（如"关于……的报告"）
- 主送机关：顶格书写，后加全角冒号
- 正文结构：基本情况 → 主要做法/成效 → 存在问题 → 下一步打算
- 报告中不得夹带请示事项；结尾用语："特此报告"等

### 请示
- 标题：发文机关 + 事由 + 文种（如"关于……的请示"）
- 主送机关：只写一个主送机关，不得多头主送
- 一文一事；正文结构：请示缘由 → 请示事项 → 请求语
- 结尾用语："妥否，请批示"；落款：发文机关署名 + 成文日期

### 批复
- 标题：发文机关 + 事由 + 文种（如"关于……的批复"）
- 主送机关：来文机关，顶格书写，后加全角冒号
- 正文结构：引述来文（文号 + 标题）→ 批复意见 → 结尾
- 结尾用语："此复"；落款：发文机关署名 + 成文日期

### 议案
- 标题：发文机关 + 事由 + 文种（如"关于……的议案"）
- 主送机关：本级人民代表大会或其常务委员会
- 正文结构：缘由 → 案由/方案 → "请审议"
- 落款：发文机关署名 + 成文日期

### 函
- 标题：发文机关 + 事由 + 文种（如"关于……的函"）
- 主送机关：商洽对象机关，顶格书写，后加全角冒号
- 正文结构：缘由 → 商洽/询问/答复事项 → 结尾
- 结尾用语："特此函商""请予函复""此函"等；落款：发文机关署名 + 成文日期

### 纪要
- 标题：会议名称 + 纪要（如"……会议纪要"）
- 无主送机关；开头列明时间、地点、主持人、出席/列席人员
- 正文：会议概况 → 议定事项（分条）
- 落款：会议名称 + 日期

## 检索策略

详见 `references/party-building-search.md`。

核心方法：使用 Tavily 的 `site:` 操作符限定搜索共产党员网（12371.cn）和党建网（dangjian.cn），采用多轮递进式检索：

1. **第 1 轮**：宽泛检索，针对核心主题
2. **第 2 轮**：精准检索，针对特定表述/引用文件
3. **第 3 轮**：深挖疑点，验证疑似过时表述

多平台结果合并去重，按时效性排序，取 Top 10 提取全文供 LLM 参考。

## 批注格式

- 使用 Word 原生 Comment 功能，在段落右侧显示批注气泡
- 按严重程度设置高亮：🔴 红色 / 🟡 黄色 / 🔵 绿色
- 每条批注包含：级别、问题类型、具体说明、修改建议、参考依据
- 文末不生成汇总表（已移除）

## API 接口

```
POST /api/v1/review/document
Content-Type: multipart/form-data
```

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:---:|:------:|------|
| `file` | File | ✅ | — | 待审核文档（.docx / .pdf，≤ 10MB，与 API 网关请求体上限一致） |
| `doc_type` | string | ❌ | 自动识别 | 文种，15 种法定文种之一（决议/决定/命令（令）/公报/公告/通告/意见/通知/通报/报告/请示/批复/议案/函/纪要） |
| `severity_filter` | string | ❌ | `all` | `all` / `critical+important` / `critical` |
| `annotate` | bool | ❌ | `true` | `true`=生成带批注的 .docx；`false`=仅返回 JSON |

响应：`annotate=true` 时返回 `download_url` + `summary` + `issues`；`annotate=false` 时仅返回 `summary` + `issues`。

## 部署

详见 `references/deployment.md`。

部署依赖链：Hermes Agent（含内置本技能）+ 审核模块代码 + MinIO + Tavily API Key（可选）+ LLM API Key。
不需要 Open WebUI、RAGFlow、Langfuse。
推荐 Docker 部署，交付包见仓库 `deploy/review/`（compose 编排 + 部署说明 + 验收测试脚本）。
定制审核标准时，复制本技能到 `~/.hermes/skills/official-document-drafting/document-review/` 修改即可（用户部署优先于仓库内置）。

## 防编造约束

- 每一条批注必须基于实际检索到的权威文件内容
- 批注中的参考依据必须包含文件来源和日期
- 当检索未找到明确对应时，标注"未在权威来源中检索到对应表述，请人工核实"
- 不得对政策方向、政治立场做出主观判断，只做事实性对比

## 与其他技能的关系

- `official-document-drafting`：负责起草公文，本技能负责审核已起草的公文
- 两者互补：起草 → 审核 → 修改 → 再审核，形成完整闭环
